## 宿題

- 取り組んだレベル：発展
- やったこと：ベンチマーク **SWE-bench Verified** を調べた。
  - データセット：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
  - 資料：論文 https://arxiv.org/abs/2310.06770 、公式 https://www.swebench.com/ 、OpenAI の紹介記事 https://openai.com/index/introducing-swe-bench-verified/ 、OpenAI のその後の投稿 https://openai.com/ja-JP/index/why-we-no-longer-evaluate-swe-bench-verified/
  - データセットから、次の3問を読んだ（全文は載せない）。
    - `astropy__astropy-14309`（難易度ラベル：<15 min）：`identify_format("write", Table, "bububu.ecsv", None, [], {})` が `IndexError` になる、というバグ。課題文に、原因と思われるコミットと、エラーの出る行（`args[0]`）が書いてある。直す場所は `is_fits` の数行。通すべきテストは1件。
    - `astropy__astropy-12907`（15 min - 1 hour）：入れ子にした `CompoundModel` で `separability_matrix` が、入れ子にしない場合と違う結果になる、というバグ。例が3つ書いてあるが、原因は書かれていない。実際の修正は `separable.py` の1行（`= 1` を `= right` にする）。通すべきテストは2件。
    - `astropy__astropy-13398`（1-4 hours）：ITRS から AltAz / HADec への変換を、ITRS の中で直接行う、という機能追加の提案。バグ報告ではなく、方針の提案と、動作するという草案のコードが書いてある。課題文には「屈折（refraction）はまだ入れていない」とある。一方、通すべきテスト4件のうち2件は名前に `with_refraction` が付き、パッチには `add_refraction` / `remove_refraction` がある。議論（`hints_text`）で屈折に触れているのは1回だけで、「追加と除去は動いている」と書いてある。パッチは298行。
  - 作り方（OpenAI の紹介記事より）：元の SWE-bench は、12 個の Python リポジトリの GitHub の課題から作った 2,294 件（論文）。Verified は、OpenAI と SWE-bench の作者が、ソフトウェア開発者 93 人（Python の経験者）に、テストセットからランダムに選んだ 1,699 件を確認してもらって作った。1件につき3人が別々に判定し、最も重い判定を採用した。事前に、50件の判定テストに通った人だけが参加した。判定する項目は、課題文の仕様不足（0〜3）、テストが妥当な解決策を落とさないか（0〜3）、難易度（時間の見積り）、自由記述の指摘。結果は、仕様不足の指摘が 38.3%、テストが妥当な解決策を落とす可能性の指摘が 61.1%、全体で 68.3% が除外対象。残りから 500 件を選んだ。
  - 採点：エージェントは、課題文とコードを見て修正パッチを作る。テストは見せない。修正後に、指定されたテスト（`FAIL_TO_PASS` と `PASS_TO_PASS`）がすべて通れば、解決とする。
  - その後の監査（OpenAI の2026年2月23日の投稿より）：OpenAI は、Verified のスコアの報告をやめた。理由は2つ。(1) テストが正しい解法を落とす：o3 が64回の実行で一貫して解けなかった138問（500問の27.6%）を、1問につき6人以上のエンジニアが確認したところ、59.4% に、テストか課題文の重大な問題があった。内訳は、実装の詳細を強制する厳しいテスト 35.5%、課題文にない機能を調べるテスト 18.8%、その他 5.1%。(2) 学習データへの混入（汚染）：テストしたすべてのフロンティアモデルが、正解パッチか課題文の内容を再現できた。
- 結果：
  結論：コードの修正（パッチ）とエージェントの回答（文章）では、LLM の出力に求めるものが違う。そのため、下の違いは、それぞれの評価セットの質を比べる根拠にはできない。

  今日の評価セットとの違い：

  | | SWE-bench Verified | 今日の評価セット |
  |---|---|---|
  | 件数 | 500件 | 10件 |
  | 評価の対象 | コードの修正（パッチ） | エージェントの回答（文章） |
  | 問題の由来 | 実際の GitHub の課題とプルリクエスト | 講師が種類を分けて作成（失敗も混ぜてある） |
  | 作成・確認 | 93人が確認、1件につき3人、最も重い判定を採用 | 講師1人が作成 |
  | 採点 | テストの実行 | 人と LLM が、基準ごとに T / F / unsure で判定 |
  | 採点の確認 | テストの妥当性を人が確認した | 人のラベルとの一致率を見る |

  - 件数：500件に対して10件。10件では、1件の判定が変わるだけで一致率が10ポイント動くため、一致率の差が偶然かどうかは言えない。
  - 件数を増やしやすいか：正解を機械で決められるかで大きく変わる。Verified はテストの実行で決まる。今日の評価セットは、基準ごとの T / F / unsure の判定に頼り、unsure は人が確認するため、件数を増やすほど人手が要る。

- 気づき・疑問：
  - コードの修正（パッチ）や用語集に基づく学習支援の質問応答などの分野ごとに、複数の評価セットの違いを分析しないと、評価セットの本質は学べないと感じた。
  - 13398 の「屈折」のように、課題文にない内容をテストが求めているかは、テストの中身まで読んでいないので、確かめていない。
  - 上の 59.4% は、解けなかった138問を監査した結果で、500問全体の割合ではない。全体では、どれくらいかは分からない。
